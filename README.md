# DouyinFilter Android

一个在 Android 手机上本地运行的抖音视频筛选与自动分享实验项目。

程序会自动浏览抖音短视频，对当前视频进行多帧画面分析，筛选出**以女性为主要人物、且画面具有较明显性感 / 诱惑特征**的内容；当视频同时满足人物条件和多帧内容判断条件后，再尝试自动分享给用户事先指定的抖音联系人。

整个识别过程在手机本地完成，不依赖云端识别服务。

## 这个项目会分享什么内容

程序不会因为“画面里出现女性”就直接分享，也不会只看某一张截图。

它主要同时判断两件事：

1. **人物主体**：使用 OpenAI CLIP 辅助判断画面主要人物是否为女性；
2. **画面特征**：使用 SigLIP2 显式内容分类模型判断画面中的 `Enticing or Sensual`（性感 / 诱惑）特征。

程序会连续分析多张视频画面。只有女性主体判断和多帧性感 / 诱惑特征判断同时满足，并通过最终视频级规则后，结果才会进入 `positive`，随后执行分享。

可以简单理解为：

> **自动刷抖音 → 连续分析视频画面 → 找到以女性为主体、且性感 / 诱惑特征比较明显的视频 → 满足规则后分享给指定朋友 → 不符合则继续下一条。**

## 使用的两个模型

### 1. SigLIP2 显式内容分类模型

使用：

`prithivMLmods/siglip2-x256p32-explicit-content/checkpoint-1656`

SigLIP2 的基础模型体系来自 Google。本项目实际使用的是第三方在 SigLIP2 基础上微调得到的显式内容分类模型。

模型可以输出多个类别，本项目主要读取：

`Enticing or Sensual`

可以理解为“当前画面具有性感、诱惑类视觉特征的程度”。程序会对每个采样帧分别得到一个分数，再结合多帧结果判断整条视频。

### 2. OpenAI CLIP

使用：

`openai/clip-vit-base-patch32`

CLIP 由 OpenAI 发布，本身是通用的图文对比模型，并不是专门的“女性识别模型”。

本项目利用 CLIP 判断图片与文字描述之间的匹配程度，在构建模型时预先准备女性、男性和无人场景的文字特征，最终在手机端辅助判断代表帧属于：

- 女性；
- 男性；
- 无明显人物。

它主要用于给 SigLIP2 再增加一层人物主体过滤，降低“画面分数较高，但主体并不是女性”的误分享。

## 模型是怎么变成手机能运行的版本

原始 Hugging Face 模型主要面向 Python / PyTorch 环境，不能直接按原样放进 Android 程序里运行，因此构建时会经过一次模型格式和精度转换：

`Hugging Face / PyTorch → FP32 ONNX → FP16 ONNX → Android APK`

这里有两个不同的概念：

- **ONNX** 是模型文件格式。把 PyTorch 模型导出成 ONNX，主要是为了让 Android 可以使用 ONNX Runtime 运行；
- **FP32 / FP16** 是模型中浮点数字的精度。FP32 使用 32 位浮点数，FP16 使用 16 位浮点数。

简单理解：

`FP32：一个浮点数通常占 4 字节`

`FP16：一个浮点数通常占 2 字节`

因此从 FP32 转成 FP16 后，可以明显降低模型文件体积、内存占用和内存带宽压力，更适合手机本地推理。FP16 仍然是浮点计算，并不是 INT8 量化。

当前 APK 中实际使用的两个模型为：

- `siglip2_raw_logits_fp16.onnx`：约 167 MB；
- `clip_female_vision_fp16.onnx`：约 168 MB。

两个 FP16 ONNX 模型合计约 335 MB。

其中 CLIP 还做了一步额外处理：女性、男性和无人场景的文字特征会在构建阶段提前计算好，因此手机端不需要重复运行完整的 CLIP 文本编码器，主要保留实际需要的视觉推理部分。

## 为什么不是看一张图就决定

实际测试中，单张截图容易受到视频转场、局部画面和偶然高分影响，因此当前程序采用多帧视频级判断。

主要参数：

- 目标采样：18 帧；
- 最大采样：20 帧；
- 采样间隔：300 ms；
- 最大采样窗口：8 秒；
- 切换视频后等待：950 ms；
- SigLIP2：两批 9 帧流水线推理；
- CLIP：从均匀时间位置和 SigLIP2 高分帧中挑选代表帧；
- 最终使用女性 Gate 与 A/B/C/D 多帧规则判断。

程序会综合观察高分帧强度、高分帧数量、Top-K 平均值和连续性，而不是“某一帧超过阈值就分享”。

## 完整运行流程

运行后，程序会循环执行：

1. 自动切换到下一条抖音视频；
2. 等待视频页面稳定；
3. 在约 5 秒时间内采集目标 18 帧画面；
4. 使用 SigLIP2 计算每帧的性感 / 诱惑类视觉分数；
5. 从代表帧中使用 OpenAI CLIP 辅助判断女性 / 男性 / 无明显人物；
6. 使用女性 Gate 和多帧规则得到 `positive / border / negative / insufficient`；
7. 只有 `positive` 才进入分享流程；
8. 定位当前视频的真实分享按钮；
9. 精确匹配用户设置的联系人；
10. 确认联系人点击和发送状态后，只执行一次发送；
11. 单次分享失败时尝试恢复视频页，然后继续下一条。

## 手机端实现

- **屏幕采集：** Android MediaProjection；
- **本地推理：** ONNX Runtime Android；
- **自动操作：** Android AccessibilityService；
- **默认推理后端：** CPU；
- **试验选项：** NNAPI；
- **架构：** `arm64-v8a`；
- **最低 Android API：** 28。

模型输入画面只在内存中用于推理，本项目不会主动把模型截图保存到手机相册。

程序会在应用私有外部目录保存有限大小的运行诊断文本日志，主要记录采样耗时、模型耗时、分享步骤和异常状态。日志滚动保存，总量约 5 MiB，不用于云端分析。

## 首次使用

1. 从 Release 页面下载 APK；
2. 安装并打开“抖音筛选分享”；
3. 填写并保存需要分享的联系人昵称；
4. 开启无障碍服务；
5. 授权屏幕捕获；
6. 等待本地模型加载完成；
7. 打开抖音；
8. 点击悬浮条上的“开始”。

联系人昵称采用精确匹配。当前程序不会为了寻找联系人而无限横向滚动联系人列表。

## 源码构建

模型权重不直接提交进 Git 仓库。GitHub Actions / `tools/export_models.py` 会从第三方公开模型来源获取权重，生成 Android 使用的 FP16 ONNX，再编译 APK。

主要源码：

- `AutomationController.java`：自动循环、18 帧采样、SigLIP 流水线；
- `ModelEngine.java`：SigLIP2 / CLIP 推理和视频级判断；
- `ScreenCaptureService.java`：内存屏幕采集；
- `TapAccessibilityService.java`：悬浮条、上滑和系统手势；
- `ShareFlowV7.java` / `ShareFlowV8.java`：当前分享流程与失败恢复；
- `TraceLogger.java`：滚动诊断日志；
- `tools/export_models.py`：模型导出与 FP16 转换。
